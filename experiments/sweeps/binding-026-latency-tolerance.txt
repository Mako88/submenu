Sweep 026 -- the architecture's headline claim, on a mechanism that works
=========================================================================

IN PLAIN TERMS
--------------
The whole point of this architecture is that it should survive being spread over
the internet, where the "well done" signal arrives late. Nobody has ever tested
that for a mechanism that actually does anything.

This tests it on the one that works. When the late signal arrives, the neuron
looks back at how active it just was -- through a window about 50ms wide. Arrive
150ms late and that window has mostly emptied, so there should be nothing left
to learn from.

If the gain fades with delay exactly as that window empties, we know precisely
what limits us. And the last condition widens the window on purpose: if that
brings the gain back at intercontinental delay, then tolerating latency is a
*setting we choose*, not a limit we're stuck with. That would be the useful
answer.

QUESTION
--------
AUDIT.md has carried this as the highest-value pending item since it was
written, and the README says it plainly:

  "The other half -- that the eligibility traces absorb a late *modulator*, so
   credit assignment survives a wide-area network -- is the harder claim and the
   one the design actually rests on, and it has not been run at twenty seeds."

Conduction delay between columns is measured and free (75x costs -0.048, i.e.
nothing). What has never been measured is whether *learning* survives a late
modulator. That is the half the distribution thesis depends on.

WHY THE EXPERIMENT AUDIT ASKED FOR WOULD NOT ANSWER IT
--------------------------------------------------------
AUDIT proposes running `plexus-experiment.yml` at `modulator_lag=200`, which
tests the three-factor rule under lag. **That rule is worth -0.003 at p = 0.79
with no lag at all.**

Measuring whether a null degrades is not a test of latency tolerance. Whatever
comes back -- null at lag 200, null at lag 0 -- the honest reading is "there was
nothing there to lose", and the sweep would produce a reassuring number that
means nothing. It is the same shape as sweep 022's `preset-frozen`: a condition
whose outcome is guaranteed by how it is built.

So the item is not run as specified. It is replaced.

THE RIGHT VEHICLE
------------------
Salience-gated Hebbian binding, because it satisfies both requirements the
three-factor rule fails:

  it pays        +0.074 linear decodability, 18/20 seeds, p = 0.0000 (sweep 020)
  it is          it reads the modulator only for its *presence*, and scores
  latency-       `act_fast` -- a `tau_act_fast = 50ms` window on the neuron's own
  sensitive      activity -- at the instant the modulator lands. A late modulator
                 scores a window that has already decayed.

That second property is what makes this a real test rather than a hopeful one.
Binding *should* degrade with lag, on a timescale the code states outright, and
the question is whether it does and how fast.

CONDITIONS  (20 seeds, 300 episodes, 96 neurons, column lr 0, drain pinned at 200)
------------------------------------------------------------------------------------
  off-lag0      no binding, lag 0        the standing baseline
  off-lag150    no binding, lag 150      **the sanity condition**
  on-lag0       binding, lag 0           the standing +0.074
  on-lag25      binding, lag 25          half a time constant
  on-lag50      binding, lag 50          one time constant
  on-lag150     binding, lag 150         three time constants; intercontinental
  on-lag150-slow  binding, lag 150, tau_act_fast 250

`drain_steps` is **pinned at 200 for every condition**, never left to track the
lag. Sweep 013 lost an entire run to that: the silent tail scaled with the lag,
so a *frozen* column shifted -0.062 at p = 0.0011 between lag settings and the
comparison was measuring tail length. `off-lag150` against `off-lag0` is the
check that the fix holds -- if those two differ, this sweep is void and says so
rather than being interpreted.

PREDICTION (recorded before the run)
--------------------------------------
The mechanism gives an arithmetic prediction rather than a guess. `act_fast`
decays as `exp(-lag / tau_act_fast)` with tau = 50, so the fraction of the
activity window still present when the modulator lands is:

  lag 0     1.00      lag 25    0.61      lag 50    0.37      lag 150   0.05

If the gain is proportional to that fraction, scaling the established +0.074:

  off-lag0        0.802   (established)
  off-lag150      0.802   MUST match off-lag0 within 0.01, or the run is void
  on-lag0         0.876   (established, +0.074)
  on-lag25        0.845 to 0.860     gain +0.043 to +0.058
  on-lag50        0.825 to 0.845     gain +0.023 to +0.043
  on-lag150       0.802 to 0.815     gain +0.000 to +0.013, probably null
  on-lag150-slow  0.840 to 0.865     gain restored to +0.038 to +0.063

**The central claim: binding's gain decays with modulator lag on a scale set by
`tau_act_fast`, and is null or nearly so at lag 150.** So latency tolerance for
the mechanism that works is *not* free -- it is bought by one time constant.

**And the second claim is the one that matters: `on-lag150-slow` restores most of
it.** If raising `tau_act_fast` from 50 to 250 recovers the gain at
intercontinental lag, then latency tolerance here is a **parameter, not a
property** -- something the model can be configured for rather than something it
either has or lacks.

WHAT EACH OUTCOME MEANS, NAMED IN ADVANCE
-------------------------------------------
  decay + recovery    Latency tolerance is a tunable time constant. The
                      architecture's claim survives in a *narrower and more
                      useful* form than the README states, and the README gets
                      rewritten to say which parameter buys it and what it
                      costs in credit precision.

  decay, no recovery  Something other than the window is broken by lag. Then
                      binding is genuinely latency-bound and the distribution
                      thesis loses its second half for the one mechanism that
                      works. That is the outcome that would most change the
                      project and it is the one to be most careful not to
                      explain away.

  no decay at all     Would mean `act_fast` is not what gates binding, since
                      three time constants of decay changed nothing. That
                      contradicts sweep 020's connection test
                      (`test_binding_scales_with_how_active_the_neuron_was`) and
                      the right response is to distrust this sweep, not to
                      celebrate.

The third is worth stating because it is the outcome that would read as good
news, and it is the one that would mean the instrument is broken.

WHAT THIS DOES NOT TEST
------------------------
The eligibility trace. `tau_eligibility` is the mechanism the README's claim is
actually *about*, and it belongs to the three-factor rule, which does not work.
So this sweep tests latency tolerance for the mechanism this project has, not
for the one it was designed around. The README must say that rather than letting
a result about binding stand in for a claim about credit assignment.

SETTINGS
--------
20 seeds, 300 episodes, 500 collection episodes, 96 neurons, column lr 0,
drain_steps 200 everywhere, `tau_act_fast` 50 except where stated.

  off-lag150 vs off    +0.000   0/20   p = 1.0000
  on-lag25   vs off    +0.016  12/20   p = 0.1610
  on-lag50   vs off    +0.011  10/20   p = 0.4184
  on-lag150  vs off    +0.001   7/20   p = 0.8849
  on-lag150-slow vs off +0.000  9/20   p = 1.0000
  on-lag150-slow vs on-lag150  -0.001  7/20  p = 0.8719

THE SANITY CONDITION PASSED AND THE BASELINE MOVED ANYWAY
-----------------------------------------------------------
`off-lag150` matched `off` to +0.000 on 0 of 20 seeds at p = 1.0000. The
sweep-013 confound this sweep was written to avoid is genuinely fixed: pinning
`drain_steps` does hold the tail constant across lag settings.

**And the baseline is 0.620 against the 0.802 that sweeps 015 through 025 all
measured.** That is not a small drift. It is the largest single movement any
baseline has made in this project.

WHAT I DID
-----------
`--drain-steps` was added to `binding.py` for this sweep with a default of
**200**. The four standing conditions -- `off`, `on`, `lateral`, `lateral+on` --
are invoked without the flag, so they took the default. Before this sweep
`binding.py` never passed `drain_steps` at all, so `Plexus` used
`drain_steps = modulator_lag = 0`.

So every condition in the file gained a 200-step silent tail per episode. Sweeps
022-023 established that the homeostatic operating point carries most of the
column's representation quality, and 200 extra silent steps per episode move
exactly that. The baseline fell 0.182.

**A new flag's default is a silent change to every existing condition.** Third
instance in this project: sweep 003 ran with a `PRETRAIN` default that made it
test nothing, sweep 013 lost a run to the drain tail itself, and now this. The
default is corrected to 0 -- reproducing what every prior sweep ran -- and
conditions that want a tail pass it explicitly.

WHY THE LAG NUMBERS CANNOT BE READ
------------------------------------
Every lag condition is null against `off`, which looks like a clean answer:
binding's gain is gone by lag 25 and never returns. It cannot be read that way,
because **there is no lag-0 reference at the same tail.** `on` in this run has
the 200-step tail too, but it is not in the paired list, and without
`on-lag0 vs off-lag0` there is no way to separate

  "binding decays with lag"   from   "binding produces nothing at drain 200"

and the second is entirely plausible given the baseline moved 0.182. Reporting
the decay would be exactly the failure this sweep refused to commit when it
declined AUDIT's version of the experiment: measuring whether a null degrades.

The irony is on the record deliberately. This sweep's own QUESTION section
rejects an experiment for lacking a working mechanism to degrade, and then
ships without the condition that would prove its own mechanism was working.

WHAT THE RE-RUN ADDS
---------------------
Two conditions that should have been there from the start, both at the same
200-step tail as every lag condition:

  off-lag0   no binding, lag 0, tail 200   -- the reference the gains are against
  on-lag0    binding,    lag 0, tail 200   -- proves binding works in this regime

and the pairs are re-pointed so every comparison is against `off-lag150` or
`off-lag0` rather than the tail-free `off`. `off-lag150 vs off-lag0` remains the
sweep-013 check.

If `on-lag0 vs off-lag0` comes back null, the mechanism does not survive the
tail and the lag question needs a different configuration entirely -- which
would itself be worth knowing, and is a finding about `drain_steps` rather than
about latency.

THE MISSING REFERENCE CHANGES THE READING COMPLETELY
------------------------------------------------------
`on-lag0` beats `off-lag150` by **+0.127 on 19 of 20 seeds at p = 0.0000**. So
binding works fine at drain 200 -- better in absolute terms than the +0.074 it
gives at drain 0, from a baseline the tail has dropped to 0.620.

That is the condition the first run omitted, and without it the identical set of
nulls could equally have meant "binding produces nothing in this regime". It
does not. **The nulls at lag 25 and beyond are a decay of a real gain, which is
what this sweep set out to measure and could not previously claim.**

  lag      gain      as a fraction of the lag-0 gain
    0    +0.127      1.00
   25    +0.016      0.13    (null)
   50    +0.011      0.09    (null)
  150    +0.001      0.01    (null)

`eff_rank` tells the same story independently and monotonically: 15.28 at lag 0
against the 20.61 baseline, then 19.10, 20.27, 20.61. The mechanism's structural
footprint fades on the same schedule as its decodability gain.

THE CENTRAL CLAIM IS REFUTED IN ITS NUMBER AND CONFIRMED IN ITS FORM
----------------------------------------------------------------------
Predicted, from `act_fast` decaying at `tau_act_fast = 50`:

  lag 25   retain 0.61  ->  gain +0.043 to +0.058     measured +0.016  (0.13)
  lag 50   retain 0.37  ->  gain +0.023 to +0.043     measured +0.011  (0.09)
  lag 150  retain 0.05  ->  gain +0.000 to +0.013     measured +0.001  (0.01)

The decay is real and exponential, and it is **four times faster than
predicted**. At lag 25 the prediction expected 61% of the gain to survive; 13%
did. Only the lag-150 band, which predicted approximately nothing, contained the
answer -- and a band that wide is not evidence.

AND THE SECOND CLAIM -- THE ONE THAT MATTERED -- IS FLATLY REFUTED
-------------------------------------------------------------------
`on-lag150-slow` raises `tau_act_fast` from 50 to 250 and was predicted to
restore +0.038 to +0.063 of gain at intercontinental lag. It restored
**+0.000, on 9/20 seeds, at p = 1.0000** -- and is indistinguishable from
`on-lag150` too, so the parameter did not move the outcome at all.

This is the outcome the note named in advance as "the one that would most change
the project and the one to be most careful not to explain away": decay with no
recovery. Latency tolerance for the mechanism that works is **not** the tunable
parameter the note hoped for.

WHY, MEASURED RATHER THAN ARGUED  (experiments/lagwindow.py)
--------------------------------------------------------------
Both failures have one cause, and it was sitting in the rule the whole time.
`_bind` commits a **product of two traces with different time constants**:

    dW  ~  post x pre
    post = act_fast / baseline     tau_act_fast = 50
    pre  = the branch filter       tau_branch   = 15     <-- never named

A product decays at the sum of the rates, so the window is

    1/tau_eff = 1/tau_act_fast + 1/tau_branch    ->    tau_eff = 11.5, not 50

`experiments/lagwindow.py` measures this directly -- the actual size of the
weight update binding commits, as a function of how late the modulator arrives
-- across three parameter settings:

    tau_act_fast   tau_branch    product predicts    measured (tail fit)
         50            15             11.54               11.87   (+2.9%)
        250            15             14.15               15.25   (+7.8%)
         50            60             27.27               28.68   (+5.2%)

Every one within 8%, and every one *above* the prediction by a few per cent --
`post` is clipped at 5.0, so the earliest lags sit on the ceiling and contribute
no decay, which biases any fit slightly wide. `act_fast` alone (50, 250, 50) and
`pre` alone (15, 15, 60) are both refuted at every setting, by margins of 3x to
17x rather than by per cent.

The window is the product, and **a product is dominated by its shorter
constant**, which is why raising `tau_act_fast` five times over widened the
window from 11.9 to 15.3 -- 28%, against a lag of 150. `on-lag150-slow` was
tuning the term that was not limiting.

WHAT THIS COSTS AND WHAT IT BUYS
----------------------------------
The lever is `tau_branch`, and raising it 15 -> 60 widens the window 11.9 -> 28.7,
while raising `tau_act_fast` 50 -> 250 buys 11.9 -> 15.3. Five times the one
parameter is worth less than four times the other, and that ratio is the whole
finding:
a factor of 2.4 for a factor of 4. So latency tolerance *is* buyable -- but not
from a plasticity setting. `tau_branch` is the branch filter in the **forward
path**: it sets how the column integrates its input in the first place, not how
it learns. Buying latency tolerance here means changing what the column
computes, and whether a column with `tau_branch = 60` still decodes anything is
not known.

That is sweep 030, and it is now a sharp question with an arithmetic prediction
attached instead of a hope.

A note on the honest ceiling: even at `tau_branch = 60` the window is 29 steps.
Intercontinental lag at 1ms/step is 150. Nothing in this family of parameters
reaches it, and the recovery would have to come from somewhere else entirely --
holding the modulator's arrival against a longer trace that the *rule* keeps,
rather than one the forward path happens to leave lying around.

THE PROBE HAD THE PROJECT'S OWN BUG IN IT FIRST
-------------------------------------------------
`lagwindow.py`'s first version measured a single binding event and reported
`tau_eff = 15.4` -- exactly `tau_branch`, with `act_fast` contributing no decay
whatsoever. That looked like a clean finding and was an artefact of the
instrument.

On the *first* `_bind` call, `act_slow` has had exactly one update, so the
sample-count debias returns `act_fast` itself and `post = act_fast / baseline`
is identically 1.0 regardless of what the activity was. The probe had divided
the quantity it was measuring by itself -- standards rule 7, in the measuring
device rather than the mechanism, and one call away from being written up as a
result about binding. Fixed with a `warmup` of binding events before the
measured one; the docstring keeps the number so the next person reads it where
they would trip over it.
