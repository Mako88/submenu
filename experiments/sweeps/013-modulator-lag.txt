Sweep 013 -- does a late modulator actually cost anything?
==========================================================

WHY THIS EXISTS
---------------
Found by the audit in experiments/sweeps/AUDIT.md, not by a bug. The
measurement was never wrong; it was narrower than the claim resting on it.

"Latency tolerance" has been covering two different claims:

  (a) inter-column CONDUCTION DELAY is free. Measured: 2ms -> 150ms costs
      -0.048 across 5 delays x 4 seeds. Frozen columns, so no learning-path bug
      can touch it. Valid.

  (b) the eligibility traces absorb a LATE MODULATOR, so credit assignment
      survives a wide-area network.

(b) is the one the architecture rests on, and it has never been run. Every
recorded sweep set MODULATOR_LAG=0. It appears in a unit test and as a
condition in experiments/ablation.py, and that is all.

The two are not interchangeable. A longer conduction delay on a frozen
reservoir is close to just a different random projection, which is why (a) came
out flat and why it is not very surprising that it did. A late modulator is a
different kind of problem: the trace has to still hold what produced the
decision when the feedback finally lands, and tau_eligibility is 70ms against a
lag of 200 steps. There is a real mechanism that could fail here.

QUESTION
--------
Does a 200-step modulator lag change the plastic-vs-frozen comparison, relative
to the same comparison at zero lag?

Note what this can and cannot show. The rule is already null at zero lag
(five sweeps, most recently -0.001 at p=0.97), so this cannot demonstrate that
learning *survives* the lag -- there is no effect left to preserve. What it can
show is whether the lag makes things actively WORSE, which is the failure mode
the eligibility trace is claimed to prevent. A rule that is merely inert at
zero lag and actively harmful at 200 would mean the trace is not doing the job
it is described as doing, and that is worth knowing regardless of whether the
rule ever starts working.

PREDICTION (recorded before the result)
---------------------------------------
The lag makes no significant difference, because there is no effect at zero lag
for it to degrade. Confidence high on that, and it is a weak prediction.

The interesting number is the frozen condition, which should be *identical*
across lag settings -- a frozen column ignores the modulator entirely. If
frozen accuracy moves between the two runs by more than seed noise, something
reads the modulator that should not, and that is a locality bug rather than a
latency result.

Second prediction, lower confidence: mean |dW| per episode in the plastic
condition falls under lag, because a modulator arriving 200 steps after a trace
with a 70ms constant lands on a trace decayed by exp(-200/70) = 0.06. If that
is what happens, the honest conclusion is that tau_eligibility and the lag
budget are the same number doing two jobs, which the config docstring already
flags as the obvious next design step, and this would be the measurement that
forces it.

SETTINGS
--------
20 seeds, 400 episodes, 24 neurons, plastic lr 5e-3, tau_elig 70,
MODULATOR_LAG=200, SURROGATE=graded, ELIG_MODE=magnitude, READOUT_RULE=delta.
Identical to sweep 008 in every respect except the lag.

Better control than 008, by accident: adding AUDIT.md under experiments/sweeps/
tripped the same path filter one commit earlier, so "plexus experiment" run #21
executed the whole 20-seed comparison at MODULATOR_LAG=0. The only difference
between that commit and this one, anywhere under plexus/ or in e2e.py, is 18
lines of README. So #21 and #22 are a matched pair differing in exactly one
parameter, which is a cleaner comparison than reaching back to sweep 008 across
several intervening changes. Use #21 as the control.

RESULT -- 20 paired seeds
-------------------------
                       frozen           plastic      paired diff        p
lag 0   (run #21)   0.592 +/- 0.059  0.590 +/- 0.060     -0.001      0.909
lag 200 (run #24)   0.530 +/- 0.037  0.531 +/- 0.040     +0.001      0.915

The primary prediction held, and was as weak as advertised: the lag changes
nothing about plastic-vs-frozen, because there was no effect at zero lag for it
to degrade.

The secondary prediction is the one that paid, and it did not hold.

THE CONTROL MOVED
-----------------
It said: the frozen condition should be *identical* across lag settings,
because a frozen column ignores the modulator entirely -- apply_modulator
returns immediately when learning is off -- and anything else is a bug.

Frozen, same 20 seeds, lag 0 vs lag 200:
  0.592 -> 0.530, paired difference -0.062, lower on 17/20 seeds, p = 0.0011.

So the lag was observable in a condition where it is unobservable in
principle. Two candidates: a locality bug, or something about the harness.
It is the harness, and the mechanism is exact.

Each episode ends with a drain tail as long as the lag, so that a modulator
still in flight is not discarded at the episode boundary. The tail is not
inert. Homeostasis keeps adapting through those extra silent steps, on
near-zero activity. Measured directly on a frozen column over 120 episodes:

                 steps    threshold   sparsity   knee    engagement
  lag 0          48,000     0.2948     0.0289   0.2308     0.1112
  lag 200        72,000     0.2311     0.0189   0.1746     0.0926

24,000 extra silent steps, and the column settles at a different operating
point. `modulator_lag` was therefore never only a lag -- it was a lag *and* a
33% longer silent period *and* a lower effective threshold, and any comparison
across it confounded all three.

CONCLUSION
----------
Sweep 013's design is invalid, and its null result says nothing about latency
tolerance. Recorded rather than deleted, because the confound is the finding
and because the prediction that caught it is the reason this file format
exists: had the sweep only reported "no significant difference, p = 0.92" it
would have looked like a clean confirmation of the architecture's central
claim, and it was not one.

FIX
---
`Plexus` and `DistributedPlexus` take `drain_steps`, defaulting to the lag so
existing behaviour is unchanged, but settable so that compared conditions share
a tail. experiments/e2e.py now pins it at 200 for every condition. Two tests:
that a frozen column's threshold, knee and weights are bit-identical across
lag settings when the tail is held constant, and that a tail shorter than the
lag raises rather than silently discarding every learning signal.

Sweep 014 should re-run this properly. The question is unanswered.
